# P101 One sync command for every store, 2026-10-07

[ADR-0057](../adr/0057-one-sync-command.md) records the decision. This file records the evidence.

### Why

On 2026-10-06 the owner asked that the move to the Cosmos projection (P100) come with "the same command for user
addition sync which checks if it's in named value or cosmos and sync accordingly across the scripts". Today
`scripts/Sync-ClaudeAccess.ps1 -User` refuses on a named-value gateway (`scripts/Sync-ClaudeAccess.ps1:144`), the
sync does not read the tier groups P100 records on the gateway (`entitlement-groups`), and AUM's Direct
publication runs a full sync for one developer's change (`scripts/Invoke-ClaudeFinOps.ps1:144-151`).

### Acceptance criteria

1. Given a named-value gateway, when `Sync-ClaudeAccess.ps1 -User <UPN or object ID>` runs, then
   `allow-standard`, `allow-premium` and `bu-members` are refreshed from Entra as a sync without `-User` refreshes
   them, the developer's tier as written (standard, premium or none) is printed, and the exit code is 0. With
   `-WhatIf`, nothing is written and the tier the refresh would give is printed.
2. Given a projection gateway, `-User` runs the targeted export and apply, as before P101.
3. Given no `-StandardGroup` and `-PremiumGroup`, the sync uses the groups in the gateway's `entitlement-groups`,
   then those of a decision record of this gateway, then the default names. A group that `entitlement-groups`
   names and Microsoft Graph does not find stops the sync before any write, with a remedy. `premium=none` means no
   premium group.
4. Given a gateway without `entitlement-groups`, a successful sync records it with the object IDs of the groups it
   used. `-WhatIf` and a failed sync record nothing.
5. Given `-StandardGroup` or `-PremiumGroup` that resolve to other object IDs than the gateway records, the sync
   refuses before any write and names `-RecordGroups`. With `-RecordGroups` it syncs and then records the new
   groups.
6. Given AUM's Direct `developer add` or `remove`, the bridge passes the developer's object ID as `-User`, and
   reports the published tier.
7. The callers keep working: `scripts/Manage-ClaudeBusinessUnits.ps1`, `scripts/Set-ClaudeDeveloper.ps1`,
   `scripts/Invoke-ClaudeFinOps.ps1`, `scripts/ClaudeTurnstileApply.ps1`, `deploy.ps1`, the installer and the update
   flow (migration 0004 reads and writes `entitlement-groups` through the shared module).
8. Live, on disposable gateways: on named values, removing the signed-in user from the standard group and running
   `Sync-ClaudeAccess.ps1 -User` gives 403, and re-adding and running it again gives 200; the gateway records
   `entitlement-groups` after its first sync. On the projection, the same pair gives 403 and 200 (P98's run,
   repeated at P101's head). AUM's add and remove on a projection gateway is measured for U25.
9. README, SETUP, UPDATE-AND-CHANGE, SECURE-PROJECTION and AUM describe one command for every store.

### Slices

1. `scripts/ClaudeEntitlementGroups.ps1`: parse and format `entitlement-groups` (moved from
   `scripts/ClaudeEntitlementMigration.ps1`, which then dot-sources it), and resolve the tier groups in the order
   of criterion 3.
2. `Sync-ClaudeAccess.ps1`: the group order, the stop on a missing recorded group, `-RecordGroups`, and recording
   `entitlement-groups` after a successful sync.
3. `Sync-ClaudeAccess.ps1 -User` on named values: the whole refresh and the tier report, `-WhatIf` included.
4. AUM: `developer_publish` passes `-User` and returns the tier; pytest and the bridge tests.
5. Callers, printed commands and docs.
6. Live runs, mutations, council, gate.
