# P102 Azure AI Content Safety screening of Claude requests at the gateway, 2026-10-06

[ADR-0055](../adr/0055-content-safety-screening.md) records the proposed decision. This file records the contract for the implementation packet.

### Why

The owner's request on 2026-10-06:

> Another feature parity is adding the content safety resource in the APIM for requests policy test this after the Migration path is done or parallelly whicever is possible as we need to check for the Claude apis and content safety resource

The gateway currently authenticates Claude Code callers, checks entitlement and budgets, and forwards Anthropic Messages requests to Claude models in Microsoft Foundry. Microsoft Foundry's Claude hosting comparison says Anthropic safety systems are active for Claude models, but it does not provide a Claude-specific configurable Azure content filter in the deployment table. P102 adds an optional Azure AI Content Safety resource and APIM request-screening path before Foundry.

The spike on 2026-10-06 found that APIM's built-in `llm-content-safety` policy partially covered Anthropic Messages bodies: it blocked harmful user strings and text blocks, a jailbreak and a harmful streaming request, but missed harmful `system` strings, harmful `system` blocks and harmful `tool_result`, and it returned 403 for a benign prompt over 10,000 characters. A custom policy that called `text:shieldPrompt` and `text:analyze` blocked T3-T8 and T10, passed T1, T2, T9 and T11, and blocked a harmful request before real Claude. The custom-policy added latency was 711-2,220 ms for passed requests and 672-966 ms for blocked requests.

### Decisions

ADR-0055 proposes:

- a custom APIM policy fragment, not the built-in `llm-content-safety` policy, for the default P102 path;
- screening the system prompt plus the newest user turn only;
- Prompt Shields `userPrompt` from newest user text and `documents` from newest user `tool_result` text;
- harm analysis of system plus newest user text and newest user tool-result text;
- newest-part truncation at the documented Content Safety budgets, with `truncated=true` logged;
- `content-safety-mode` named value: `block`, `audit` or `off`, with opt-in deployments defaulting to `block`;
- `content-safety-threshold = 2` with `FourSeverityLevels` across `Hate`, `Violence`, `SelfHarm` and `Sexual`;
- a Bicep Content Safety module, APIM identity role assignment, named values and policy fragment;
- installer support for new gateways and update-flow support for existing gateways;
- request-only screening; response and streamed-output screening out of scope;
- Anthropic-style error JSON with no prompt text in the reason;
- Application Insights trace metadata that records decisions and severities, never prompt text.

### Acceptance criteria

1. Given `content-safety-mode` is `off`, when `POST /v1/messages` reaches the gateway, then no Content Safety `send-request` call is emitted and the existing Foundry forwarding path is unchanged.
2. Given `content-safety-mode` is `block`, when a benign string user message is sent, then the offline policy test shows one Prompt Shields call, one analyze call, no block, and the original request body remains available for Foundry.
3. Given `content-safety-mode` is `block`, when a benign content-block user message is sent, then the offline policy test shows the text block in `userPrompt` and the request passes.
4. Given `content-safety-mode` is `block`, when a harmful user string is sent, then the offline policy test returns 403 with Anthropic-style `content_safety` JSON and no prompt text.
5. Given `content-safety-mode` is `block`, when a harmful user text block is sent, then the offline policy test returns 403 before Foundry.
6. Given `content-safety-mode` is `block`, when the `system` field is a harmful string, then the offline policy test includes it in the analyze text and returns 403 before Foundry.
7. Given `content-safety-mode` is `block`, when the `system` field is harmful text blocks, then the offline policy test includes those blocks in the analyze text and returns 403 before Foundry.
8. Given `content-safety-mode` is `block`, when the newest user message contains harmful `tool_result` text, then the offline policy test includes it in Prompt Shields `documents`, includes it in analyze text, and returns 403 before Foundry.
9. Given `content-safety-mode` is `block`, when a jailbreak prompt is sent, then the offline policy test blocks through Prompt Shields and the response reason does not include the prompt.
10. Given `content-safety-mode` is `block`, when an image-only request is sent, then the offline policy test passes and logs an empty text slice rather than a prompt body.
11. Given `content-safety-mode` is `block`, when `stream: true` is set on a harmful request, then the request is blocked before forwarding and no response-stream handling is added.
12. Given a benign Claude Code-shaped conversation with more than 10,000 characters of earlier context and a short newest user turn, when the offline policy test runs, then only the system prompt and newest user turn are screened, the request passes, and `truncated=false` for the newest turn.
13. Given the newest user turn exceeds a Content Safety budget, when the offline policy test runs, then the newest part is screened, `truncated=true` is logged, and the policy does not claim that earlier omitted text was screened.
14. Given a fabricated harmful earlier turn and a benign newest user turn, when the offline policy test runs, then the request passes and the result is recorded as the documented fabricated-history limit, not as a safety pass.
15. Given Content Safety returns an error or times out, when `content-safety-mode` is `block`, then the gateway returns 503 with Anthropic-style JSON and `Retry-After`; when the mode is `audit`, then the request continues and the error is logged; when the mode is `off`, then no call is attempted.
16. Given the deployment templates are compiled, when the offline deployment tests inspect them, then they find a Content Safety account with `kind: ContentSafety`, SKU `S0`, custom subdomain, disabled local auth, the APIM principal role assignment, the Content Safety named values and the policy fragment include.
17. Given a supported region and an unsupported region fixture, when the deployment readiness tests run, then the supported region passes and the unsupported region blocks before any write with a remedy that cites the current Content Safety region table.
18. Given the trace policy runs in any mode except `off`, when the offline logging test inspects metadata, then it finds mode, decision, booleans, numeric severities, threshold, truncation and elapsed milliseconds, and does not find prompt text, system text, tool text, model output, image bytes or matched snippets.
19. Live: given a disposable gateway with Content Safety enabled in `block`, when T1-T11 run, then the observed decisions match the custom spike: T1, T2, T9 and T11 pass; T3-T8 and T10 block; latency p50 and max are recorded.
20. Live: given a real Claude deployment behind the disposable gateway, when a benign request and a harmful request run, then the benign request returns 200 from Claude and the harmful request returns 403 before Foundry.
21. Live: given a Claude Code-shaped long conversation and a fabricated-history request, when both run, then the long newest-safe request passes, the fabricated-history case records the documented limit, and neither log row stores prompt text.
22. Live: given the disposable resources, when teardown runs, then the Content Safety role assignment is absent and the resource group deletion is confirmed or recorded as deleting with a follow-up command.
