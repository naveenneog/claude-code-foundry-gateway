# P113 Preflight proves group-creation privilege before an absent tier group is called creatable, 2026-10-12

This file records the contract and the evidence. No ADR: the fix extends `entra.groupNames`, an
existing preflight check, with the same unproven-is-reported caution
`scripts/ClaudeProjectionChecks.ps1`'s 'Resolver registration' check already uses for app-registration
rights; it adds no new store, boundary or dependency (the same reasoning P96 used for its own
fixes-from-a-live-deployment packet, which also carried no ADR).

### Why

A customer deployment (`RG-PCSAZINFYAI102`) reached "Entra groups" with both tier groups absent,
warned `Could not create 'INFYAIAZ103STD' - your tenant may restrict group creation` and continued;
the next step, "Sync entitlement", then threw an uncaught `AADSTS53003` (Conditional Access blocked
Graph token issuance for the operator) after the gateway, its API and its policies were already
deployed. `Install-ClaudeGateway.ps1 -Preflight` already runs before any write and already reads
whether each named tier/business-unit group exists, but an **absent** group was unconditionally noted
`'name' is created by the run` - it never checked whether the signed-in account can actually create
one. A tenant that disables self-service group creation (or where Conditional Access blocks the
operator's Graph access entirely) was only discovered live, mid-deployment.

### Acceptance criteria

1. Given `-Preflight` (or `-PlanOnly`/the guided flow) finds a named tier or business-unit group
   absent, it additionally reads the tenant's default-user-role permission
   (`authorizationPolicy.defaultUserRolePermissions.allowedToCreateSecurityGroups`, Microsoft Graph).
2. Given that permission is `true`, `entra.groupNames` keeps today's result: the group is noted
   `created by the run`, and the check passes if nothing else fails.
3. Given that permission is `false`, missing, or not a boolean, or the read itself fails for any reason
   (Conditional Access, Graph access denied, not signed in), `entra.groupNames` is a FAIL naming every
   absent group together and a remedy: the customer Entra admin creates the group(s) first, grants the
   operator Groups Administrator, User Administrator or Global Administrator, or turns on "Users can
   create security groups" - never a silent pass. A directory role grants creation regardless of the
   tenant default, so an unconfirmed read is reported, not asserted blocked.
4. The read is one Microsoft Graph call regardless of how many groups are absent (not one per group),
   using this file's own `Invoke-ClaudeInstallAzRead` (`az rest`) idiom rather than the raw-REST
   `Get-GraphToken`/`Invoke-ClaudeGraphRead` pair, so the existing az-stub child-process preflight test
   harness (`tests/InstallerCheckpointStubs.ps1`) covers it without a live network dependency.
5. Every existing preflight scenario is unaffected: a world that does not set `groupCreateAllowed`
   keeps the default (`true`), so an absent group is still noted `created by the run`.

### Evidence

- `tests/Test-InstallerPreflight.ps1`, scenario `group-create-blocked`
  (`$w['groupCreateAllowed'] = $false`, both tier groups absent): `entra.groupNames` is a FAIL naming
  `'claude-code-standard'` and `'claude-code-premium'` together, with `Groups Administrator` in both
  the message and the remedy, and `Users can create security groups` in the remedy.
- The pre-existing `pass`, `one-unit` and `units` scenarios (which leave `groupCreateAllowed` unset,
  and whose worlds never pre-populate tier groups) keep `entra.groupNames` as PASS, proving the
  default behaviour is unchanged.
- `tests/InstallerCheckpointStubs.ps1` stubs
  `az rest --method get --url https://graph.microsoft.com/v1.0/policies/authorizationPolicy` ahead of
  the pre-existing generic `rest*` ARM-role-assignment stub, returning
  `defaultUserRolePermissions.allowedToCreateSecurityGroups` from the world (default `true`).
- Property name verified against
  [Microsoft Graph `defaultUserRolePermissions`](https://learn.microsoft.com/en-us/graph/api/resources/defaultuserrolepermissions)
  (retrieved 2026-10-12): `allowedToCreateSecurityGroups` - "Indicates whether the default user role
  can create security groups."
