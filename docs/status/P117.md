# P117 Cross-tenant production pilot on the customer Cosmos estate, 2026-10-15

### Why

The live customer estate is in tenant `d2885cb9-fed7-44e5-bf35-834991ed5eb0`,
subscription `66db7d6e-9810-4e77-853a-164a7dbde561`. It already contains
Standard v2 API Management, Cosmos DB, `ccof-poc-vnet`, private endpoints and
private DNS. Claude is served from the separate FDPO tenant. The existing
gateway proves that APIM can use a preconfigured secret named value to obtain a
client-credential token from FDPO without exposing the secret.

P116 does not yet deploy this shape. Its Foundry resource reference and managed
identity grant assume the deployment subscription, and its existing-VNet path
owns private DNS zones rather than reusing customer zones.

### Scope

P117 adds an opt-in cross-tenant Foundry path for a reused APIM instance and an
opt-in existing private-DNS path for a customer VNet. The default same-tenant
managed-identity and projection-owned DNS behavior stays unchanged.

The live configuration contains the P116 nine plans and 47 access profiles plus
48 independent business units. "48 BUs" is interpreted as 48 business units in
addition to the 47 profile groups. A count detector in the deployment-config
test prevents either number changing silently.

### Acceptance criteria

1. A deployment config binds the customer subscription, `ccof-poc-apim`,
   `ccof-poc-vnet`, the existing endpoint and APIM subnets, three new dedicated
   projection subnets, and explicit existing private-DNS zone IDs.
2. Cross-tenant mode takes an explicit FDPO endpoint, tenant ID and client ID,
   references the existing secret named value without reading or copying its
   value, and creates no managed-identity role assignment on the FDPO account.
3. Same-tenant mode remains byte-for-byte equivalent at the policy boundary:
   the APIM managed identity obtains the Cognitive Services token.
4. Existing private-DNS mode creates no replacement zone or duplicate VNet
   link. New private endpoints attach zone groups to the supplied zone IDs.
5. The deployment creates or adopts exactly 47 access-profile groups and 48
   business-unit groups, publishes the nine-plan catalog, and leaves group
   membership under Entra administration.
6. One pilot identity receives one whole profile and one business unit after
   sync. An allowed FDPO model returns 200; a disallowed family returns 403.
7. Moving the pilot between profiles and business units, then running targeted
   sync, changes the Cosmos record and request result without a redeployment.
8. The existing `claude-messages` API and its revision remain unchanged. P117
   uses the separate `claude-foundry` API and `/claude` path.
9. The scheduled job stays manual until one attended full sync and one manual
   job execution succeed. Missing tenant-admin Graph permission remains an
   explicit refusal rather than a fallback.
10. Live resource IDs, group IDs and tenant-specific generated files remain
    under ignored `onboarding/` paths. Source control contains only the
    placeholder deployment example and redacted evidence.
