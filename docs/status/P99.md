# P99 Directory-scale snapshot transfer, 2026-10-06

[ADR-0053](../adr/0053-parallel-compressed-runner-transfer.md) records the decision. This file records the evidence.

### Why

The deployer's populate step, the switch's snapshot compare and `Sync-ClaudeAccess.ps1` send a full
snapshot to the in-network runner through `az container exec`. Before P99 that transfer sent one
uncompressed base64url chunk per exec, one exec at a time. A snapshot of about 40,000 developers filled
the snapshot's 2-hour apply-by time. A larger transfer was refused before it started
([ADR-0052](../adr/0052-cosmos-default-installer.md), amendment 2). The ROADMAP acceptance for P99: a
snapshot of 500,000 records is applied and compared.

### Decisions

ADR-0053:

- the file is compressed with gzip, encoded as base64url, and split into parts of one exec command each;
- at most 16 parts are in flight at once, each in its own Azure CLI process;
- each part is acknowledged with its own index and length, and retried for at most 3 attempts;
- one exec assembles the parts in order, decompresses them, removes the part directory and prints the
  SHA-256, which the caller checks;
- an estimate before the first exec, and the measured rate during the transfer, refuse or stop a
  transfer that would end after the apply-by time, with nothing written;
- when `az` is a PowerShell function, the parts go one at a time in-process.

### Acceptance criteria

1. Given a file, `Send-RunnerFile` leaves identical bytes at the destination (the SHA-256 matches) and
   removes the part directory. When `az` is an application, more than one exec runs at once and never
   more than `-Parallel`.
2. The parts carry the file gzip-compressed: the number of part writes is the base64url length of the
   compressed file divided by the part size, rounded up.
3. Every exec command is under 5,000 characters, has no space inside its program, and contains none of
   `"`, `%`, `+`, `&`, `|`, `<`, `>`, `^` or `!`.
4. A part whose exec fails, or that prints no matching `ok <index> <length>`, is retried after 2 seconds
   and then 4 seconds. A part that fails 3 times stops the transfer: no assembly runs, the part directory
   is removed, and the error names the part, the attempts and the remedy, with sanitized output.
5. An assembly whose SHA-256 differs from the local file's fails with "did not arrive intact".
6. A transfer estimated to end after the apply-by time is refused before the first exec. A transfer
   whose measured rate projects past that time stops, removes its parts and writes nothing. Both
   messages give the measured 500,000-record figure and the optional sync job's command.
7. When `az` is a PowerShell function or alias, the parts go one at a time in-process.
8. The three callers keep passing the snapshot's apply-by time and are otherwise unchanged.
9. Live: a synthetic 500,000-record snapshot is sent to a disposable runner, applied by the writer and
   compared with `--compare-snapshot` with no differences, inside its apply-by time. The times are
   recorded and the resources are deleted.
10. When `az` is an application, an exec that does not answer within `-ExecTimeoutSeconds` is stopped and
    its part retried. A transfer that stalls is stopped before its apply-by time without waiting for the
    stalled exec.
11. A transfer estimated at a minute or more prints its parts and minutes before it starts and its progress
    about once a minute; a shorter transfer prints nothing.

### Tests

`tests/Test-RunnerTransfer.ps1` (registered in `Test-All.ps1`) runs `Send-RunnerFile` against a local runner
emulator. Like the runner, the emulator splits each exec command on spaces, URL-decodes it and runs the
`node` program, with `/work` mapped to a scratch folder. The suite runs it two ways: in process, with `az` as
a PowerShell function, and in parallel, through a fake `az.cmd` that runs each exec in its own process.
Faults are injected per part: a transient failure, a permanent failure, an exit 0 without the
acknowledgement, a part acknowledged but missing at assembly, and a wrong hash.

- RED at `e3407091` with the test written: 34 assertions, 20 failed for the intended reasons (no part
  protocol, no `-Parallel`, `-SecondsPerExec` or retries, and the old refusal text). One assertion passed
  vacuously on zero parts and was tightened to require a payload.
- GREEN at `4fc209bb`: 37 of 37. The first GREEN run found that .NET writes no gzip bytes for an empty file;
  the assembly writes an empty file for an empty payload.
- `3116690f`: the up-front refusal test passes `-ReserveSeconds 0`, so it fails if the estimate understates
  the transfer, and a destination that would close the program's quotes is refused. 38 of 38.

Changes to existing tests:

- `tests/Test-ProjectionRunnerLifecycle.ps1`: the deadline test sent 600,000 `x` characters, which gzip now
  compresses to one part, so the refusal no longer came from the transfer's length. It sends 1.5 MB of random
  text with `-ReserveSeconds 0`. Its assertion that the refusal names ROADMAP packet P99 now checks the
  500,000-developer figure, because P99 is no longer planned work. 14 of 14.
- `tests/TestProjectionFixture.ps1` emulates the new protocol in memory (part directory, acknowledged parts,
  assembly with gzip decompression and SHA-256), so the deployer, switch and sync suites keep exercising
  real transfers.

The suites that load `scripts/ClaudeRunner.ps1` or the fixture pass at `4fc209bb`: council 95, preflight
187, deployer compare 8, installer 44, flow switch, runner lifecycle 14, sync scripts 29, switch evidence,
package and secure projection. "Projection deployer and installer switch wiring" failed only when run
alongside the council suite, which writes switch backups into the same folder; `Test-All.ps1` runs it in
the exclusive lane, and alone it passes. `tests/Test-ProjectionPreflightNegative.ps1`, a manual harness
that `Test-All.ps1` does not run, fails its baseline at `main` `8a4be16` as well as here; it is a ROADMAP
follow-up.

### Architecture

No component, identity, schedule or network path changes. The operator's machine still reaches the
runner only through `az container exec`; only the transfer protocol over that path changes. The
architecture diagrams and `docs/ARCHITECTURE.md` do not describe the protocol, so they are unchanged.
