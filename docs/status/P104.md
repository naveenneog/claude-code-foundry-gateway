# P104 The projection sync job runs on a schedule the admin sets, 2026-10-08

[ADR-0058](../adr/0058-scheduled-projection-sync.md) records the decision. This file records the contract and the evidence.

### Why

The owner's request on 2026-10-07:

> One more addition to the sync container app jobs, can this interval be set by the admin with minimum of 2 hours as base, so just adding a developer in UI would be good enough to make the change and the sync container will syncs every two hours and updates their tiers. But make sure it only updates the added developer or removed developer changes in tiers gets updated not all entitlement is removed, I think this is significant usability update take this on priority now. and merge to our installer when chosed with cosmos based projection. This is a high improvement with low changes make this first before other updates in my opinion.

> if 30 mins is possible then great

> radding in UI mean adding the user in the tier group like claude-code-standard and BU entra groups , with scheduled jobs it can pick them up and give permission, not via AUM finops or turnstile

### Acceptance criteria

1. Given the projection is chosen, when the installer runs without an interval, then it deploys the sync job with the cron expression `0 */2 * * *`, and the review lists the interval, the runs per month and the cost.
2. Given `-ProjectionSyncInterval` `30m`, `1h`, `2h`, `3h`, `4h`, `6h`, `8h`, `12h` or `manual`, the job gets the mapped trigger. `none` deploys no job. `15m`, `0m`, `24h`, `2 h` and `abc` are refused before any Azure call, and the message lists the accepted values.
3. Given a scheduled run, only changed developers are written or deleted: an unchanged record is not written, an added developer is written, a removed developer is deleted, and a tier change is written.
4. Given a scheduled (`--graph`) run whose plan deletes more than max(10, 10% of the existing entitlement records), nothing is written, no status record is written, the failure line has stage `removal-ceiling` with both counts and the attended command, and the exit code is not zero. A plan at the ceiling applies. A snapshot run through `Sync-ClaudeAccess.ps1` applies the same plan.
5. Given the job identity does not hold `GroupMember.Read.All`, the installer says so and prints the grant command; given it holds it, the installer says so. The installer makes no Microsoft Graph write.
6. Given an installed gateway, `scripts/Set-ClaudeProjectionSyncSchedule.ps1 -Interval 4h` changes the trigger and the no-success alert together, with the deployed image digest and no image build; `-Interval manual` removes the schedule and the no-success rule.
7. The compiled template reads 2 x interval + 15 minutes in the no-success rule for every interval, with one rule name; a manual job has no such rule. The deploy script removes the earlier `-no-success-45m` rule.
8. SECURE-PROJECTION and AZ-COMMANDS give the interval, the time to effect, the Graph grant, and the Azure CLI and portal steps to change the interval; README and SETUP list the installer parameter; the AZ-COMMANDS guard covers the new parameters.
9. Live: an install with the projection and `-ProjectionSyncInterval 30m` shows a scheduled execution in the job's execution history within 35 minutes. Without the Graph grant the execution stops at the Graph stage and writes nothing. U17 blocks the positive path in the reference tenant; the offline runs prove it with a fake directory.

### Architecture

The sync job, its environment, registry, identity and alerts exist since P94. The projection diagram's sync job line (`docs/architecture/05-projection.json`) now reads "every 2 h by default; 30m-12h or manual", re-rendered with `node guide/render-architecture.mjs`, and `docs/ARCHITECTURE.md` describes the schedule.
